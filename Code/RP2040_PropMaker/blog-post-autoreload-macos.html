TL;DR: If CircuitPython keeps printing “Code stopped by auto-reload” when you haven’t saved anything, macOS is writing to the CIRCUITPY drive behind your back. Extended attributes — not your code — are the trigger. A Quick Look in the Finder is enough to cause it.

The symptom

You’re running a piece on a CircuitPython board, watching the serial console, and out of nowhere:

color 6/15: hue 149 deg  rgb (0, 255, 122)

Code stopped by auto-reload. Reloading soon.
soft reboot

code.py output:

No file was saved. No editor was open. The board restarted anyway, mid-animation.

Auto-reload is the feature that makes CircuitPython pleasant: drag a file onto the drive and it runs. It works by restarting code.py whenever the filesystem is written. The catch is the word whenever — it doesn’t care who wrote, or whether anything meaningful changed.

Finding the culprit

Listing the drive told the story immediately. Alongside the real files sat a set of AppleDouble sidecars:

$ ls -la /Volumes/CIRCUITPY/
._code.py             Sep 15 14:08
._color_switcher.py   Sep 15 15:14
._ext_button_test.py  Sep 15 14:45
._orange_fade.py      Sep 15 14:44
.fseventsd/
.Trashes  .Trash-1000
.metadata_never_index
code.py               Sep 15 14:53
color_switcher.py     Sep 15 15:13

Look at the two timestamps in the middle. color_switcher.py was written at 15:13. Its sidecar ._color_switcher.py was written at 15:14 — a full minute later. That’s macOS touching the volume well after the save finished, which is exactly why the reload arrives at a moment that feels unrelated to anything you did.

Why the sidecars exist

CIRCUITPY is formatted FAT, which has no way to store macOS extended attributes. When a file carries them, macOS stores them in a parallel ._filename file. Every time an attribute changes, that sidecar is rewritten — a filesystem write, and therefore a reload.

So what attributes are on there?

$ xattr -l /Volumes/CIRCUITPY/color_switcher.py
com.apple.provenance
com.dropbox.attrs

$ xattr -l /Volumes/CIRCUITPY/code.py
com.apple.lastuseddate#PS
com.apple.provenance
AttributeWritten byWhen
com.apple.lastuseddate#PSmacOSWhenever a file is opened or previewed
com.apple.provenancemacOS (Ventura and later)Stamped on files generally
com.dropbox.attrsDropboxRides along when you copy from a Dropbox folder

com.apple.lastuseddate#PS is the troublemaker. macOS updates it when a file is merely accessed — no edit required. The file’s contents are identical; the sidecar still gets rewritten; the board still reboots.

Quick Look is enough

The reproduction is almost comically simple. Select a .py file on the CIRCUITPY drive in the Finder and press space. Quick Look opens a preview, macOS stamps the last-used date, the sidecar is rewritten, and your board restarts.

Browsing the drive in a Finder window can do it too, by creating or updating .DS_Store.

It isn’t Spotlight, and it isn’t only Dropbox

Two reasonable suspects turned out to be innocent.

Spotlight was already excluded. The drive carries a .metadata_never_index file, and mdutil confirms it:

$ mdutil -s /Volumes/CIRCUITPY
/System/Volumes/Data/Volumes/CIRCUITPY:
	Indexing and searching disabled.

Adding the volume to the Spotlight Privacy list would change nothing.

Dropbox contributes, but isn’t required. Note in the output above that code.py has no Dropbox attribute — and it still has a ._code.py sidecar. Keeping your source outside Dropbox removes one of three attributes and leaves the problem intact.

Why CircuitPython can’t just ignore these files

The obvious fix would be for auto-reload to skip writes to ._*. It can’t, and the reason is structural: the board exposes its flash as USB mass storage. The host writes raw blocks, not files. From the board’s side, macOS updating a sidecar and you saving code.py look the same. There is no filename to filter on.

Worth adding to the picture: macOS has also been known to delay writes to small FAT volumes by 5–30 seconds, which further decouples the reload from anything you remember doing. That behaviour is covered in an earlier post here.

What actually helps

1. Clean the drive

Remove the existing sidecars and strip the attributes that cause them:

dot_clean -m /Volumes/CIRCUITPY
xattr -cr /Volumes/CIRCUITPY

dot_clean -m deletes the ._* files. xattr -c clears extended attributes and -r recurses. Neither touches file contents — your code is untouched.

Only point this at the board. Running xattr -cr across your home directory or a Dropbox folder would strip sync metadata and quarantine flags you want to keep.

2. Copy without metadata

The Finder always preserves extended attributes; there’s no preference to disable it. Copying from the Terminal with -X leaves them behind:

cp -X ~/path/to/color_switcher.py /Volumes/CIRCUITPY/

Verify with xattr -l on the copy — clean means no output, and no ._ twin appears.

3. Adjust two habits

  • Quick Look and edit files in your source folder, not on the drive. Same file, no consequence.
  • Keep the CIRCUITPY Finder window closed while code is running.

4. Turn auto-reload off when it matters

For an installation you don’t want restarting itself, put a flag at the top of code.py:

lock_reload = False
if lock_reload:
    import supervisor
    print("Locking reload - need to manually reset after code changes")
    supervisor.runtime.autoreload = False

Flip lock_reload to True when the piece is running for real, and back to False while you’re developing. A single boolean is easier to find than a commented-out line, and the printed reminder saves you the confusion of wondering why your saves have stopped taking effect — because once it’s locked, you have to reset the board manually for changes to load.

When this actually matters

It’s worth being clear about the scope, because the problem is narrower than it first feels:

  • Running on battery or a wall charger: no issue at all. Nothing mounts the filesystem, so there are no writes to react to.
  • Developing, with the drive mounted: stray reloads are noise. You were about to restart the code anyway.
  • Running the finished piece while still plugged into a computer: this is the case that bites — a stray preview resets your installation during setup or a long test. Disable auto-reload here.

Diagnosing it yourself

If you want to know whether a restart was a phantom write or a genuine crash, print the reason at the top of your code:

import supervisor
print("run reason:", supervisor.runtime.run_reason)

It will report AUTO_RELOAD for a filesystem write, which distinguishes macOS noise from an actual problem in your program.

Tested on an Adafruit Feather RP2040 Prop-Maker with the CIRCUITPY drive mounted on macOS.
